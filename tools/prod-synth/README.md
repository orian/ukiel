# prod-synth — the generator runbook

Compiles the anonymized workload profile in `docs/prod-info/` into a portable,
deterministic, **synthetic** event fixture: sorted Parquet plus a versioned manifest.

It is **offline**. It needs a Rust toolchain and nothing else — no PostgreSQL, no
Kafka, no object store, no running Ukiel. That is enforced, not promised:
`tests/boundary.rs` inspects the dependency graph that actually gets built and fails
if a service client ever appears in it.

## What the artifact is, and is not

It reproduces the **geometry** of an observed workload — tenant activity skew,
part-to-tenant membership, key sparsity — from anonymized aggregates. It contains no
production rows, no real tenant identifiers, and no real column values.

Every manifest says so, and every reader in the pipeline refuses an artifact that does
not. No number drawn from this fixture describes a real production system.

## Install

```bash
cargo install --path tools/prod-synth --root ~/.local
prod-synth --help
```

Works from a fresh checkout, from any directory. The tool has no notion of a
repository: every input and output is named on the command line, and there is no
default `bench/` path.

## Use

```bash
# Read the profile and print what it does and does not tell us.
prod-synth profile --profile docs/prod-info --report /tmp/profile.json

# Compile it into a fixture. --output is mandatory.
prod-synth generate --tier baseline --profile docs/prod-info \
  --output bench/datasets/prod-synth/baseline

# Prove the bytes you have are the bytes that were made. Contacts nothing.
prod-synth verify bench/datasets/prod-synth/baseline/manifest.json
```

`--tenants`, `--rows-per-shard`, `--shards` and `--seed` override the tier defaults.
Every override is recorded in the manifest, so a report can never claim to be a stock
tier when it is not.

### Tiers

| tier | tenants | rows/shard | size | purpose |
|---|---:|---:|---:|---|
| `smoke` | 1,000 | 100k | ~5 MB | parser/generator/load correctness |
| `baseline` | 10,000 | 30M | ~1.3 GB | the query and catalog baseline; the only tier the distribution gates bind on |
| `shape` | 142,066 (estimated) | 100M | ~4.5 GB | optional cardinality confirmation; **not** an acceptance gate |

**`baseline` is 30M rows per shard, not the 5M the plan tiers it at.** The two cannot
both hold. A baseline topology has ~168k tenant-part memberships and every membership
must carry at least one row — otherwise the part does not contain the tenant the
catalog says it does, and the key filter under test would be answering about a graph
the files do not have. At 5M rows that floor, not the activity weights, decides the row
count of **70% of tenants**: the median tenant's weight-proportional share is 2 rows
while its membership floor is 11, and the measured p90/p50 activity ratio collapses to
18 against the source's 98. `heavy`, `median` and `light` stop being different queries.
26.4M rows is where the median tenant's weight-share clears its floor; 30M clears it
comfortably, and the skew gates pass there.

## Determinism

Same profile + same config + same seed → **byte-identical** files. The PRNG is
`splitmix64/v1`, named in every manifest and pinned by a golden-sequence test; the
generator uses no wall clock, no `thread_rng`, and no hash-map iteration order.

```bash
prod-synth generate --tier smoke --profile docs/prod-info --output /tmp/a
prod-synth generate --tier smoke --profile docs/prod-info --output /tmp/b
diff -r /tmp/a /tmp/b   # identical
```

If the numbers ever change, the golden test fails and the version string must change
with them — a fixture generated by a different PRNG is a different fixture.

## Portability

Generate on one machine, `verify` on another, then load. The manifest carries digests
of the four profile files, the topology, and every Parquet part; `verify` re-checks all
of them plus the Parquet footers, the row census, and the membership truth, without
touching a network.

Never regenerate a fixture inside the loader or the benchmark runner. Neither can, and
that is deliberate: a tool that can rebuild its own inputs will eventually rebuild them,
under a seed nobody wrote down.

## What is derived, and what is invented

**Derived from the profile** (and gated against it):

- the part-to-tenant membership graph, and every part's key range, density and fanout;
- the tenant activity skew;
- the number of parts, and their relative sizes.

**Declared synthetic** — the profile says nothing about any of it, and the `ValueModel`
in every manifest says so verbatim:

- the event vocabulary, URLs, hosts and SDK names;
- the person population and `distinct_id` repetition;
- the `properties` JSON, whose three promoted keys exactly equal the `mat_*` columns.

**Recorded as provenance only, and never reused**: ClickHouse byte totals, part types,
and merge levels. A ClickHouse merge level is not a rung on Ukiel's compaction ladder,
and copying it across would give a real number a false meaning. Every generated part is
written at one fixed non-L0 level so an idle benchmark is stable.

`properties` is `utf8`, not a JSON type — that is the physical reality of the captured
ClickHouse `String` column and all Ukiel supports today. The values are valid compact
JSON, so a future JSON plan can add extraction queries over the very same bytes.

## Fidelity gates

`generate` prints every source/generated pair, pass or fail, and refuses to publish a
`baseline` fixture that fails one. Output lands in a staging directory and is renamed
into place only after every gate passes — a half-written fixture that looks complete is
worse than none.

The distribution gates bind at `baseline` only. Smoke is too small for a distribution to
mean anything, and shape is a cardinality confirmation the plan declines to gate on. The
**structural** invariants — every part's declared range brackets its actual members, the
Parquet footers agree with the manifest, the census balances — are enforced at every tier
without exception.

## Two things the source data cannot tell you

Both are printed by `prod-synth profile`, and carried into every manifest.

**The active-tenant count is an estimate.** `sum(part.distinct_keys) /
mean(tenant.exact_parts) = 2,389,316 / 16.818 = 142,066`. It is two margins of one
bipartite graph, and it holds only if the tenant sample is uniform over active tenants
and covers the same part scope. It is not a discovered production total.

**The two capture files disagree about the part population.**
`tenant-fanout.jsonl` reports up to 63 range candidates per tenant, but
`part-geometry.jsonl` holds only 61 parts whose key range is wider than a single point —
and a single-key part is a range candidate for exactly one tenant, its own. No graph over
61 multi-key parts can put a tenant in 63 ranges. The files were captured at different
part scopes. Range saturation is therefore asserted against the achievable maximum of 61,
and the manifest carries a note saying so.
